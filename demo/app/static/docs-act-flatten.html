Flipping act → sub, governed by Ping Authorize

RFC 8693audience-scoped A special exchange that collapses the delegation chain into a single self-identity — but only where policy says it's allowed.

The one-line version. For one specific audience — a downstream event sink — the delegation chain is deliberately flattened: the root orchestration agent (the innermost act.sub) is promoted to be the token's sub, and the act chain is dropped. The agent acts as itself, not on Alice's behalf. Ping Authorize governs the flip — it only happens for the events audience, and only for an authorized agent; everywhere else the exchange stays normal nested delegation.

Why flatten at all?

Publishing an event isn't "acting for Alice" — it's the orchestration platform emitting an operational signal. Carrying Alice's identity (and the full agent chain) onto an event bus would over-share the principal and leak the delegation graph to a consumer that has no business with it. So for that one audience we swap delegation for a plain workload identity, hard-scoped so it can't be reused elsewhere.

Normal hop (banking)

{
  "sub": "alice",
  "act": { "sub": "payments-agent",
    "act": { "sub": "concierge" } }
}

Flattened (events audience)

{
  "sub": "concierge",   // ← root actor promoted
  "aud": "…/events",
  "act": {…}          // dropped
}

How the flip happens

  1. The payments agent does a second RFC 8693 exchange, this time with resource = https://events.northwind.example (the events audience).
  2. PingFederate selects an audience-scoped access-token manager (eventsFlatJwtATM) whose contract is {sub, client_id} — no act. The chain is structurally gone.
  3. The new sub is the root actor: the innermost act.sub of the incoming token (the orchestration/concierge agent), not Alice.
  4. Ping Authorize governs the exchange before it's issued — see below.

Ping Authorize is what makes it a policy, not a hack

Promoting an actor to the subject is exactly the kind of authority change that must be governed, not left to a fragile string rewrite. A policy in the Policy Administration Point — "Event-endpoint flatten governance" — is targeted at the events audience and evaluated on every exchange:

// Trust-framework policy (Symphonic), DenyUnlessPermit
TARGET   TokenExchange.requestedAudience == "https://events.northwind.example"
RULE     Permit  IF  actor is an authorized agent  // else DENY
         // applies ONLY to events-audience requests — banking exchanges are
         // NOT_APPLICABLE here, so nothing else is affected

Two things follow from letting the PDP own this:

  • The flip is authorized per-request. An unauthorized agent, or any other audience, is denied — the flatten can't be requested into existence.
  • The PDP is the durable source of the root actor. PingFederate can extract the root act.sub with an OGNL string-walk, but that's brittle; the intended path is for the audience policy to return the root actor and the mapping to source sub from the policy response — so the same Ping Authorize that permits the exchange also supplies the identity being promoted.
Deliberately not delegation. The flattened token has no act and a narrow aud. It says "the orchestration agent is publishing an event", full stop. It cannot be replayed against the banking APIs (wrong audience), and it carries none of Alice's authority.
Config-as-code. The audience-scoped ATM + selection live in demo/pingfederate/terraform/flatten.tf; the governance policy is authored via the PAP and shipped as a committed snapshot + deployment package in the policy repo (pap-profile/policies/…, deployment-packages/…) — never poked into a running server by hand.
