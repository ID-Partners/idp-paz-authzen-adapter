How the agents & services interact

Alice authorises a principal agent, which delegates to a task agent. At every resource boundary the caller does a token exchange at PingFederate for a token scoped to that resource: each agent exchanges for an MCP-audience token to call PEP #1, and the MCP service — itself an API client — exchanges for a Bank-API-audience token to call PEP #2, nesting the actor chain each hop. Both gateways and the token issuance consult Ping Authorize (the PDP) for a PERMIT/DENY. The dashed gold leg (MCP → AS) is the intended step — today the MCP forwards the agent's token; a true nested exchange there needs RFC 8693 token exchange. Nodes light up as a run progresses.

RAR — how fine-grained payment consent works RFC 9396

A coarse OAuth scope says "this agent may initiate payments." RAR (authorization_details) says "Alice approved THIS payment — $1,500 from CHK-1001 to SAV-2002" — and Ping Authorize governs it at the moment PingFederate issues the token, not just later at the gateway.

  1. The agent proposes the payment. The app (BFF) builds an RFC 9396 authorization_details entry describing that specific payment (type, amount, currency, debtor + creditor accounts).
  2. Pushed via PAR (RFC 9126) to PingFederate so the payload never rides on the browser URL, and Alice is redirected with prompt=login consent — re-authenticate + consent (RFC 9470 step-up).
  3. Governed at issuance. PingFederate's pf-rar-paz-plugin (an AuthorizationDetailProcessor) hands each entry to Ping Authorize → PERMIT ≤ AUD 2,000 / DENY above. The decision's UserID is Alice (the resource owner, folded in as _principal_sub); the agent is recorded as the actor.
  4. Alice consents. On PERMIT, the consent page shows the payment attributes (amount, from, to); she approves; the issued token carries the governed authorization_details.
  5. Governed once, not per hop. The RAR is governed at Alice's consent (the authorization endpoint) — it is not re-sent on each agent's RFC 8693 exchange (PF's exchange grant has no RAR processor; re-sending it → invalid_authorization_details). Every delegated hop inherits that governed authority via sub=alice.

Deep dives — how the identity plumbing actually works

Two write-ups on the novel token-exchange machinery behind this demo:

🔗 Token exchange in PingFederate — nested actor chains
How each delegation hop is recorded as act nesting (RFC 8693 + RFC 7519 act): the subject-token processor exposes the inbound act, and an OGNL mapping wraps the calling agent around it — delegation, never impersonation.

🔗 Ping Authorize policy-based act→sub flatten
How an audience-scoped exchange promotes the root orchestration agent (innermost act.sub) to sub and drops the chain for the event sink — governed by a Ping Authorize policy so the flip only happens where it's authorized.
