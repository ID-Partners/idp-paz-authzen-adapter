Token exchange in PingFederate — keeping a nested actor chain

RFC 8693RFC 7519 · act How each delegation hop is recorded as act nesting instead of impersonation.

The one-line version. Every agent gets its token by exchanging the token it was handed (RFC 8693). PingFederate keeps the human as sub and wraps the calling agent around the incoming act chain — so the token records who acted on whose behalf, at every hop. This is delegation, never impersonation (the actor is always visible).

Impersonation vs. delegation

An RFC 8693 exchange with only a subject_token mints a token that looks like the user obtained it themselves — the acting agent is invisible. That is impersonation, and it defeats agent identity. We instead carry an act claim, so the resource server and the audit log can always answer "which agent, for which principal?"

Impersonation ✗Delegation ✓ (what we do)
Issued tokensub: alice, no actsub: alice, act: {…}
Who acted?invisiblethe full agent chain, outside-in
Audit / disputebrokenreconstructable

The delegation chain in this demo

Alice signs in at PingFederate — OIDC login token (no act)
│ exchange (subject = Alice's token)
Concierge / principal agent — token A: sub: alice, act: {concierge}
│ exchange (subject = token A) — delegates to a task agent
Account / Payments agent — token B: sub: alice, act: {account-agent, act:{concierge}}

The chain reads outside-in: the outer sub is the principal; each act wraps the next actor down. Walk the whole chain on ingest — don't just trust the top-level sub.

// token B, as seen by the resource server
{
  "sub": "alice",                          // the human principal
  "act": {
    "sub": "urn:agent:northwind-account:v1",  // the acting agent
    "act": { "sub": "urn:agent:northwind-concierge:v1" }  // who delegated to it
  },
  "cnf": { "jkt": "…" }               // DPoP sender-constraint (RFC 9449)
}

How PingFederate is configured (3 pieces)

1 · Subject-token processor — expose the inbound act

A JWT token processor (subjectJwtProc) validates the incoming token (issuer, signature via PF's JWKS, expiry) and — the key change — publishes its act claim into the attribute contract so the exchange can read it.

attribute_contract {
  core_attributes     = [{ name = "subject" }]
  extended_attributes = [{ name = "acr" }, { name = "scope" },
                         { name = "act" }]   // ← makes subjecttoken.act available
}

2 · Token-exchange processor policy — carry sub and act through

userToAgentTE maps the subject token's sub and act straight through from SUBJECT_TOKEN, so both are available to the access-token mapping.

attribute_contract_fulfillment {
  "subject" = { source = { type = "SUBJECT_TOKEN" }, value = "sub" }
  "act"     = { source = { type = "SUBJECT_TOKEN" }, value = "act" }  // the delegator chain
}

3 · Access-token mapping — wrap this agent around the incoming chain

This is where the nesting happens. sub stays the human. act is built by an OGNL expression: the current agent's own id as a literal, wrapping whatever act arrived. An empty incoming act (the root/concierge case) yields just {sub: agent}.

"act" = { source = { type = "EXPRESSION" }, value =
  // "{\"sub\":\"<this-agent>\"" + (act==null ? "" : ",\"act\":" + act) + "}"
  '"{\"sub\":\"urn:agent:northwind-account:v1\"" +
    (#this.get("act") == null ? "" : ",\"act\":" + #this.get("act").getValue()) + "}"'
}

Each hop re-runs this, so the chain grows one layer deeper per exchange. The concierge mapping is left as-is — it is the root of the chain (it exchanges Alice's login token, which has no act), so its act is always just {concierge}.

Sender-constrained throughout. Every issued token is DPoP-bound (cnf.jkt, RFC 9449) to the requesting agent's key — the exchange attenuates authority and binds it to the holder, so a stolen token is useless without the agent's private key.
Config-as-code. All of the above lives in the repo as Terraform (demo/pingfederate/terraform/token-exchange.tf, pingidentity/pingfederate provider) and is applied to an ephemeral PF whose exported config archive is the deploy artifact — never hand-edited in the admin console.
